# A 股正式券商通道资格研究

**日期:** 2026-07-17

**历史研究问题（非当前队列）:** `哪个正式券商路径能够承载受控实盘？`

> 本文只保留券商资格研究证据；当前状态和优先级只以 [NOW](../NOW.md) 为准。

**当前结论:** `PUBLIC_EVIDENCE_COLLECTED / USER_PARKED_WITHOUT_DATE`

华西证券与平安证券都存在官方量化/程序化交易产品证据，暂时不能仅凭品牌排除任何一方。公开材料只能证明“券商有相关能力”，不能证明“用户当前账户可开通、FIN 可用 API 接入、订单回报和故障保护满足本项目”。用户已把具体账户询证、券商接入和无人确认的真实资金自动交易无限期停放并排除在第一版之外；只有 8 月 PAPER 全自动与人工操作参考稳定可用、经过实际观察，且用户明确重启后才重新规划。第一版只完成 broker-neutral/PaperBroker 能力，真实委托路径保持物理不可达，也不使用同花顺 GUI 自动化代替正式接口。

## 1. 监管与交易所边界

证监会《证券市场程序化交易管理规定（试行）》自 2024-10-08 起施行；上海证券交易所和深圳证券交易所的实施细则自 2025-07-07 起施行。正式规则明确覆盖由计算机程序自动生成或下达交易指令的投资者，客户首次程序化交易前应向证券公司报告，由证券公司核查确认后方可交易；重大变化还需变更报告。规则体系还对相关交易系统和会员提出资金证券核验、权限/阈值、异常处理、快速暂停/撤单/隔离、人工干预及交易所处理结果监控等要求；其中部分是券商/会员职责，FIN 将其作为自身额外安全基线，不把它们全部表述为个人投资者的直接法定义务。

这意味着 FIN 未来若重启真实资金自动交易，仍属于程序化交易治理范围，不能因为频率低、由 LLM 给出判断或最终落到条件单，就绕过券商确认和系统安全要求。当前 3～5 只、日线波段策略远低于规则列举的高频申报阈值，但“不是高频”不等于“不是程序化”。

8 月 FIN 只运行 PAPER 自动交易并提供只读人工操作参考，不向真实券商下单；用户在券商 App 内自行判断和手工操作属于 FIN 之外的人工行为。未来若改为“用户确认后由程序自动下达”，仍按程序化交易完成报告与券商核查，不利用人工确认去主张豁免。

## 3. 同花顺可以是候选适配层，但不能默认成为安全根

消费级同花顺条件单的官方资料说明，条件满足后才发出委托，不保证报单或成交；真实委托生成后与原条件单存在独立生命周期。另一方面，SuperMind 官方帮助公开了资金/持仓查询、限价下单、撤单、委托/成交查询、订单推送、断线重连、模拟/仿真和实盘等 `TradeAPI` 能力。因此不能把“同花顺”整体判成只有 GUI，也不能因为普通同花顺能登录某券商，就推定 SuperMind 对该账户已有实盘授权。

SuperMind 公共文档同时表明，实盘依赖付费客户端保持运行；公开材料没有证明当前支持华西或平安的普通个人实盘账户，也没有公开相应门槛、合同、费用及重启/健康检查周期。它只有在“券商明确支持 + 同花顺实盘合同 + 程序化报告覆盖 FIN 与该软件栈”同时成立时，才进入 `LiveBrokerAdapter` 候选。

所以普通条件单可以成为某些人工确认场景的执行辅助，SuperMind 也可用于仿真/接口资格测试，但在双向授权和实测前都不能自动证明 FIN 所需的：

- 稳定 `client_order_id` 与委托的一一映射；
- 提交、拒绝、部分成交、成交、撤单和未知状态的机器可追溯回报；
- 日初、盘中和日终的资金/持仓/在途委托对账；
- 主备 fencing、重启恢复和“不确定时不重复下单”；
- FIN-owned 授权过期、价格上限与资本权限的确定性执行证明。

官方参考：[同花顺条件单说明](https://search.10jqka.com.cn/school/article-detail/id/2693)、[SuperMind TradeAPI 帮助](https://quant.10jqka.com.cn/view/help/14)。GUI/RPA 自动点击明确排除，不作为失败时的 fallback；iFinD 数据 API 也不能冒充交易 API。

## 4. 给两家券商的同一份书面询证清单

询证必须绑定用户准备使用的账户，不接受“理论上支持 QMT”这种泛答复。要求营业部、客户经理或官方客服给出可留存的工单、邮件、页面或协议编号。

### 4.1 账户与合规

1. 当前个人 A 股账户能否开通 QMT/其他官方程序化交易系统；资产、交易经验、专业投资者、营业部和账户类型门槛分别是什么？
2. 5 万元与未来 50 万元账户是否适用不同权限、费用、柜台或产品？
3. 首次程序化交易报告由谁提交、需要哪些策略/软件/最高申报速率资料、审核时长多久？
4. 策略、软件版本、资金/杠杆、最大申报速率发生何种变化需要变更报告？
5. 普通 A 股、创业板、科创板、ST、融资融券账户分别支持到什么范围？第一版可接受主动禁入 ST、北交所、可转债和两融交易。

### 4.2 接口与运行环境

1. 官方支持的客户端/SDK/API 名称、版本、操作系统、Python 版本及文档获取方式是什么？
2. 是否支持行情、资金、持仓、可卖数量、当日委托、当日成交、撤单和逐笔/推送回报？
3. 是否提供仿真、沙箱或与实盘同 adapter 语义的测试环境？测试与实盘差异是什么？
4. 是否要求交易软件前台登录、验证码、人工每日登录或固定 IP/MAC；断线后如何恢复？
5. 行情是否为合法授权源，是否含源时间、买一卖一、涨跌停价、停牌和交易阶段？

### 4.3 订单语义与对账

1. 客户端能否传入稳定的自定义订单 ID；重复请求如何判重？
2. 委托 API 的同步返回和异步回报分别是什么；如何区分已拒绝、已受理、部分成交、已成交、已撤、废单与状态未知？
3. 网络在提交后断开时，如何只凭 client ID/券商委托号确定订单事实，而不盲目重试？
4. 当日历史查询保留多久；次日能否取得完整成交、资金和持仓用于重建？
5. 接口限速、单日指令数、并发连接、维护窗口和错误码文档是什么？

### 4.4 保护、主备与费用

1. 能否在券商侧预置价格上限、止损/止盈、OCO、当日过期或其他在 FIN 主机掉线后仍持续有效的保护？
2. 已触发条件单与真实委托如何关联、修改和撤销；程序停机时保护是否仍生效？
3. 是否允许一主一备/observer；如何防止两个实例同时发单，券商是否提供 session fencing 或唯一登录限制？
4. QMT/行情/API/托管/专线/交易佣金最低收费的完整成本是多少？是否有最低资产或月交易量？
5. 官方技术支持渠道、故障通告、升级节奏和紧急停用方法是什么？

## 5. 资格实测矩阵

书面答复合格后，先用官方仿真。没有等价仿真时，无专项授权只允许正式环境纯查询，以及不会离开 FIN 本地的过期/拒绝测试。任何发往正式柜台、会创建、修改、撤销委托或保护状态的请求，无论买卖、价格远近和是否预期成交，都必须取得 intent-bound 专项授权；真实资金订单继续逐单授权。

| 场景 | 必须观察的结果 |
|---|---|
| 重复提交同一 command | 只能关联同一券商委托，不能产生第二笔订单 |
| 价格越界/授权过期 | FIN 本地拒绝；即使绕过 adapter 也不能接受原始 LLM 输出 |
| 合法委托 | 同步返回、异步回报和查询结果可关联 |
| 部分成交后撤单 | 成交量、剩余量、资金、持仓与最终状态一致 |
| 提交瞬间断网 | 状态进入 `SUBMISSION_UNKNOWN`，先查询/对账，不盲重试 |
| FIN 重启 | 从不可变 journal 和券商事实恢复，不重复下单 |
| observer 误激活 | lease/fencing 阻止双 active executor |
| 主机断电 | broker-side 保护继续有效；否则经批准的冗余保护方案能接管且先对账 |
| 日初/盘中/日终对账 | 资金、持仓、可卖、委托、成交差异可检测并冻结新增风险 |

## 6. Go/No-Go 规则

### `BROKER_CHANNEL_ELIGIBLE`

`#4` 只负责证明具体账户和正式通道允许开始 conformance，不预先要求尚未实现的 adapter 证明自己。只有同时满足下列条件才可进入 `#4.5 LiveBrokerAdapter`：

- 具体账户准入、报备要求、费用和支持边界有可追溯确认；
- 已获得批准的正式接口/量化终端文档和可用仿真/UAT；没有仿真时，券商书面允许受控 conformance，并明确正式环境边界；
- 程序化报告路径和所需软件版本/测试材料已明确；若券商必须在 adapter 验证后才最终确认报告，需先书面允许 UAT/conformance，并把最终报告回执设为 #4.5 的 pre-live 硬门；
- 文档与书面答复覆盖查询、委托、撤单、回报、对账、提交未知、断线恢复、部分成交和保护能力，且不存在已知架构性否定；
- 已形成可执行的 conformance 计划，能在 `#4.5` 验证重启、主备冲突和断电保护，而不是靠口头承诺放行实盘；
- 不依赖 GUI 自动化、共享人工密码、静默追单或把条件单名称当作生命周期证据。

通过以上条件只授予“可开始实现和测试”，不授予 live 权限。实际提交/回报、断线、重启、部分成交、对账、fencing 与灾难保护证据全部归 `#4.5`；其完成后才可称 `LiveBrokerAdapter=QUALIFIED`。

首版 conformance 只测最终选定的一个券商、一个具体账户、一个官方通道和 V1 实际使用的限价订单/查询/撤单能力，不做华西 × 平安 × 同花顺 × 多账户的全排列。资本安全核心路径必须实测；券商可选功能或稀有错误码若没有可靠环境，就保持 capability 关闭并 fail-closed，待真正需要开放时再补证据。

### `BROKER_NO_GO`

任一 P0 能力只有口头承诺、不能获得正式开通、无法确定订单是否已提交、无法对账，或灾难场景只能靠人工碰运气，即为 `NO-GO`。第一版本就不包含实盘 canary；该结论只阻止后续 live 权限，不阻塞模拟盘和 broker-neutral 战术 Agent。

## 7. 未来重启条件（非当前排期）

1. 第一版不要求用户联系客户经理、营业部或客服；询证模板只在用户未来明确重启真实资金自动交易后启用，不绑定日期。
2. 用户明确重启后，因用户已有华西账户，先通过官方客服/营业部工单提交清单；华西任一硬项否定或含糊，再向平安提交同一清单，不因产品宣传贸然转户。
3. FIN 根据答复选定一个通道，再单独实现并验收 `LiveBrokerAdapter`；品牌选择不能提前侵入第一版领域合同。
4. 未取得资格前，M4、战术 Agent、模拟盘和数据观察可以继续，但真实委托路径保持物理不可达；当前不存在 9 月自治日期，未来重启也不能压缩安全观察期。
